# Архитектура

## Ключевые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Фронтенд | Next.js 14, App Router, TypeScript | Главы и темы рендерятся на сервере (SSR/SSG) и индексируются поисковиками, интерактив — в клиентских компонентах |
| Бэкенд | Route Handlers Next.js (`src/app/api`) | Один проект, один деплой, общие типы. Логика лежит в `features/*`, поэтому её можно вынести в отдельный сервис без переписывания |
| Стили | Tailwind CSS, значения только из токенов | Палитра и анимации меняются в одном файле, произвольные цвета в компонентах не появляются |
| БД | PostgreSQL + Prisma | Иерархия «глава → тема → задание» и прогресс естественно ложатся на реляционную модель, Prisma даёт типы и миграции |
| Аутентификация | JWT access (15 мин) + refresh (30 дней) в httpOnly cookie, bcrypt | Access проверяется без запроса к БД, refresh можно отозвать |
| Валидация | zod | Одна схема для проверки на сервере и типов |

## Слои и правила импорта

```
app/  ──▶  features/*  ──▶  lib/
  │            │
  └────────────┴──▶  shared/ui
```

- `app/` — только маршрутизация и сборка страниц. Бизнес-логики здесь нет.
- `features/<домен>/` — логика домена. Наружу видно только `index.ts` (безопасно для клиента) и `server/` (только сервер). Правило `no-restricted-imports` в ESLint запрещает лезть во внутренние файлы фичи.
- Фичи не импортируют друг друга по кругу. Связи: `learning` читает `content` и `auth`; `gamification` реагирует на события `learning`.
- `shared/ui/` — компоненты без знания о домене (кнопки, прогресс-бар, поля).
- `lib/` — инфраструктура: клиент Prisma, переменные окружения.

## Домены

| Домен | Отвечает за | Таблицы |
|---|---|---|
| auth | регистрация, вход, выход, сессии | User, RefreshToken |
| content | главы, темы, задания, публикация | Chapter, Topic, Task |
| learning | прохождение, проверка ответов, прогресс | TaskAttempt, TopicProgress |
| gamification | опыт, уровни, достижения | XpEvent, Achievement, UserAchievement |

## Аутентификация

1. **Регистрация / вход.** Пароль хешируется bcrypt (12 раундов). Сервер выдаёт access JWT и refresh-токен, оба в cookie с флагами `httpOnly`, `secure` (в продакшене), `sameSite=lax`.
2. **Запросы.** Access проверяется подписью, без обращения к БД.
3. **Обновление.** Когда access истёк, клиент вызывает `/api/auth/refresh`. Сервер находит хеш refresh-токена в `RefreshToken`, помечает его отозванным и выдаёт новую пару (ротация). Повторное использование отозванного токена отзывает все сессии пользователя.
4. **Выход.** Текущий refresh-токен отзывается, cookie очищаются.

В БД хранится только SHA-256 хеш refresh-токена: утечка базы не даёт войти в чужие аккаунты.

## Безопасность контента

- `Task.solution` не попадает в ответы API и клиентские компоненты. Проверка ответа — только на сервере.
- Все входные данные API проверяются zod-схемами.
- Неопубликованные главы (`isPublished = false`) видны только роли `ADMIN`.

## Переменные окружения

Описаны в `.env.example` и проверяются в `src/lib/env.ts` при первом обращении. Ошибка конфигурации видна сразу и с понятным текстом.
